# 从父架构中设计一个子模块

## 这件事到底在做什么

把父架构想成一栋已经盖好的楼。你这次只装修其中一个房间：先确认房间是哪一个、墙和水电哪些不能动，再设计房间里面如何分区。不能顺便把隔壁房间或整栋楼推倒重来。

例如，L0 里有 `MOD-AI-TUTORING`。本次只设计它的内部，可以得到 `CMP-HINT-ORCHESTRATOR`、`CMP-SOLUTION-ORCHESTRATOR` 和 `CMP-LLM-ADAPTER` 等子节点；不能修改会话模块的职责，也不能把 AI 模块私自变成独立微服务。

## 开始前准备四样东西

| 你要给的东西 | 用途 |
|---|---|
| `parent_architecture` | 上一层完整架构包。 |
| `target_node_id` | 这次要设计哪个父节点，例如 `MOD-AI-TUTORING`。 |
| `current_prd` | 这个节点自己的 PRD。 |
| `output_dir` | 新架构包放在哪里。 |

`parent_prd` 不是必须项；只有父架构包里找不到需求来源时才需要它。

## 参考文件应该按什么顺序看

这些不是要单独“运行”的子 Skill，而是每一步要看的说明。看完一份、完成对应动作后，再看下一份：

1. `input-contract.md`：确认资料齐不齐、模式是什么、输出位置会不会覆盖旧结果；有阻塞问题就先停下。
2. `parent-package-adapter.md`：认出父包是哪种结构，找到唯一的 `target_node_id`，拿到这次真正需要读的父层内容；匹配不安全就停下。
3. `parent-boundary-rules.md`：列出父层已经定好的墙、门和水电，也就是不能随便改的边界；当前 PRD 越界就停下。
4. `local-refinement-and-mapping.md`：分配当前 PRD，只设计节点内部，并用 C1-C6 检查状态、契约和流程。
5. `local-decision-queue.md`：判断问题该本层决定、留给下一层，还是必须返回父层；遇到 `return_to_parent` 就写 `parent-change-request.md` 并停下。
6. `artifact-spec.md`：前面都完成后，再按它生成七个架构文件和 `child-handoff.md`。

## 真正执行时，每一步要做什么、写到哪里

不要只读完父包后给一段总结。按下表逐步写文件，上一行没有完成就不要进入下一行。

| 阶段 | 做什么 | 写到哪里 | 可以继续的条件 |
|---|---|---|---|
| 0. 绑定输入 | 确认路径、`mode` 和输出是否安全。 | 先创建 `architecture-manifest.yaml`，写入输入路径、模式和 `draft` 状态。 | 四项必需输入齐全，且不会误覆盖旧包。 |
| 1. 找到并锁定父节点 | 识别父包类型，唯一匹配目标节点，只抽取这个节点的边界。 | 在清单写入父包类型、`node_match_evidence`、`boundary_fingerprint`；在 `01-design-context.md` 开始写父边界快照。 | 目标唯一，且关键状态、契约、约束都找得到。 |
| 2. 分配当前 PRD | 把每条需求分成继承、分配、本地或越界。 | 完成 `01-design-context.md` 的需求分配表和局部驱动。 | 没有需求被错误分给兄弟节点，也没有关键歧义。 |
| 3. 设计内部结构 | 细化内部概念，拆子节点，确定状态归谁。 | 在 `02-architecture-decomposition.md` 写子节点清单和依赖图；在 `03-state-and-data.md` 写状态清单。 | 每个子节点都有 `child_id`、职责、排除项、状态、依赖和理由。 |
| 4. 设计内部协作 | 把父层流程和契约落实为内部协作与内部契约。 | 在 `04-contracts-and-runtime.md` 写父契约实现映射、内部契约、成功/失败/生命周期流程。 | 父契约的含义和所有权没有被改掉。 |
| 5. 决策或返回父层 | 判断每个未解决问题该本层决定、交给下一层，还是返回父层。 | 在 `05-local-decisions.md` 写本层决策；需要上返时写 `parent-change-request.md`。 | 没有未处理的 `decide_now`；一旦上返父层就立刻停止。 |
| 6. 交接 | 检查七个文件，列出下一层可继续细化的子节点。 | 完成 `child-handoff.md`，把清单状态改为 `ready_for_human_gate`。 | 当前包内部一致，可以进入一次 Human Gate。 |

## 六步完成一次细化

1. **先找到正确的父节点**：确认父包是新版 L0 包还是上一层子包，并精确找到 `target_node_id`。旧包没有 ID 时，只能在 `migrate` 模式下按一个明确名称兼容匹配。
2. **看清楚哪些不能动**：记下该节点的职责、排除项、已有状态、对外契约、上下游、技术和部署限制。这就是父边界快照。
3. **把当前 PRD 分分类**：哪些是父层已经规定的，哪些是交给本节点做的，哪些只是内部细节，哪些根本不属于这里。
4. **只设计节点内部**：按职责、状态、不变量和生命周期拆成子节点。每个子节点都给一个稳定 `child_id`，让下一层能继续选择它。
5. **把内部协作讲清楚**：说明状态归谁、父契约在内部由谁实现、失败如何处理、关键流程怎样走。C1-C6 只是这一步的检查清单，不是额外工作流。
6. **做局部决定并交接**：本层能决定的就记录；需要改变父层的就写 `parent-change-request.md` 并停下来；最后交出当前层包和下一层入口。

## 你可以改什么，不能改什么

可以：节点内部的组件划分、内部状态、内部事件、内部协作、局部缓存或重试策略。

不能：父层职责、兄弟节点的数据、跨节点契约字段、父层数据库/消息队列/部署方式、是否拆独立服务。需要动这些时，使用 `parent-change-request.md` 返回父层讨论。

## 最后会得到什么

```text
architecture/
|-- architecture-manifest.yaml        # 这次设计谁、父层是谁
|-- 01-design-context.md              # 父边界和需求分配
|-- 02-architecture-decomposition.md  # 内部子节点怎么拆
|-- 03-state-and-data.md              # 状态和数据归谁
|-- 04-contracts-and-runtime.md       # 契约和关键流程
|-- 05-local-decisions.md             # 本层决定了什么
`-- child-handoff.md                  # 下一层可以继续设计谁
```

需要父层批准时，额外生成 `parent-change-request.md`，但不假装该变更已经通过。

## 什么时候应该停下来

父包读不到、目标节点不唯一、关键契约或状态信息缺失、当前 PRD 要求改变父边界、或输出会覆盖已有包但未明确要修订时，先停止并补齐信息。

本 Skill 只做架构设计，不生成代码、测试、脚手架或部署清单。每次交付最后保留一个 Human Gate，确认后才用 `[NEXT child_id]` 进入下一层。

需要看字段和例外规则时，再阅读 `references/` 下的中文文件：它们是详细说明，不是必须从头读到尾的第一入口。
